# Data Model: Database Backup System

## Overview
The backup feature does not introduce new database entities. Instead, it operates on existing tables and generates backup files in various formats. This document describes the data structures used for backup operations and temporary file management.

## Backup Request/Response Structures

### Backup Request
**Purpose**: Client request to create a backup

```typescript
interface BackupRequest {
  format: 'sql' | 'json' | 'csv' | 'sqlite_gz';
}
```

**Validation Rules**:
- `format` must be one of the four supported values
- No other fields required (one-click process)

### Backup Response
**Purpose**: Server response after backup creation

```typescript
interface BackupResponse {
  backup_id: string;
  format: 'sql' | 'json' | 'csv' | 'sqlite_gz';
  filename: string;
  size_bytes: number;
  created_at: string; // ISO 8601 timestamp
  status: 'completed' | 'failed';
  error?: string;
  download_url?: string; // Only present if status is 'completed'
}
```

**Fields**:
- `backup_id`: Unique identifier for this backup (UUID or timestamp-based)
- `format`: The backup format that was created
- `filename`: The generated filename (includes timestamp and format)
- `size_bytes`: Size of the backup file in bytes
- `created_at`: When the backup was created
- `status`: Whether backup succeeded or failed
- `error`: Error message if status is 'failed'
- `download_url`: URL to download the backup (only if successful)

### Progress Update
**Purpose**: Real-time progress updates during backup creation

```typescript
interface BackupProgress {
  backup_id: string;
  progress_percent: number; // 0-100
  status: 'creating' | 'validating' | 'completed' | 'failed';
  current_step?: string; // e.g., "Processing table 3 of 8"
  error?: string; // Only present if status is 'failed'
}
```

**Fields**:
- `backup_id`: The backup being created
- `progress_percent`: Percentage complete (0-100)
- `status`: Current stage of backup process
- `current_step`: Human-readable description of current operation
- `error`: Error message if status is 'failed'

## Backup File Storage

### File System Structure
```
backend/instance/backups/
├── {backup_id}_sql_{timestamp}.sql
├── {backup_id}_json_{timestamp}.json
├── {backup_id}_csv_{timestamp}.zip
└── {backup_id}_sqlite_{timestamp}.db.gz
```

### File Naming Convention
- Format: `{backup_id}_{format_type}_{timestamp}.{extension}`
- Example: `abc123_sql_2025-12-16_14-30-45.sql`
- `backup_id`: Unique identifier (UUID or timestamp-based)
- `format_type`: `sql`, `json`, `csv`, or `sqlite`
- `timestamp`: ISO format `YYYY-MM-DD_HH-MM-SS`
- `extension`: `.sql`, `.json`, `.zip`, or `.db.gz`

## Backup Format Specifications

### SQL Dump Format
- **File Extension**: `.sql`
- **Content**: SQL statements (CREATE TABLE, INSERT, etc.)
- **Generated by**: SQLite `.dump()` method
- **Validation**: Check for CREATE TABLE and INSERT statements

### JSON Export Format
- **File Extension**: `.json`
- **Content**: JSON object with table names as keys, arrays of records as values
- **Structure**:
  ```json
  {
    "teacher_aides": [...],
    "tasks": [...],
    "assignments": [...],
    "classrooms": [...],
    "absences": [...],
    "availability": [...],
    "requests": [...],
    "recurring_series": [...]
  }
  ```
- **Validation**: Parse JSON and verify all expected table keys exist

### CSV Collection Format
- **File Extension**: `.zip`
- **Content**: ZIP archive containing one CSV file per table
- **Structure**:
  ```
  timetable_backup_csv_2025-12-16_14-30-45.zip
  ├── teacher_aides.csv
  ├── tasks.csv
  ├── assignments.csv
  ├── classrooms.csv
  ├── absences.csv
  ├── availability.csv
  ├── requests.csv
  └── recurring_series.csv
  ```
- **Validation**: Verify ZIP can be opened and all expected CSV files exist

### Compressed SQLite Format
- **File Extension**: `.db.gz`
- **Content**: Gzip-compressed copy of the SQLite database file
- **Generated by**: Copy database file, compress with gzip
- **Validation**: Verify file can be decompressed and opened as SQLite database

## Tables Included in Backup

All tables from the existing database schema:
1. `teacher_aides` - Staff members
2. `tasks` - Task templates
3. `assignments` - Specific task occurrences
4. `classrooms` - Physical learning spaces
5. `absences` - Aide unavailability records
6. `availability` - Weekly availability patterns
7. `requests` - Teacher requests for aide support
8. `recurring_series` - Recurring task series metadata

**Note**: Backup includes all data from all tables. No filtering or date ranges.

## State Transitions

### Backup Creation Flow
```
[Request Received]
    ↓
[Creating] → Progress updates (0-80%)
    ↓
[Validating] → Progress updates (80-95%)
    ↓
[Completed] → Download URL provided
    OR
[Failed] → Error message, retry available
```

### Error States
- **Database Locked**: Retry with exponential backoff (up to 3 attempts)
- **Disk Space Insufficient**: Immediate failure, user action required
- **Permission Error**: Immediate failure, user action required
- **Validation Failure**: Immediate failure, log error, allow retry
- **Network Interruption**: Immediate failure, allow retry

## Data Integrity Rules

1. **Completeness**: All 8 tables must be present in backup
2. **Consistency**: Foreign key relationships preserved in export formats
3. **Validation**: Backup file must pass format-specific validation before download
4. **Atomicity**: Backup creation is a single operation (all tables or none)

## Temporary Storage Lifecycle

1. **Creation**: Backup file created in `backend/instance/backups/`
2. **Validation**: File validated immediately after creation
3. **Download**: File available for download via GET endpoint
4. **Cleanup**: (Future) Old backup files deleted after retention period (e.g., 7 days)

**Current Implementation**: No automatic cleanup (manual or future enhancement)
